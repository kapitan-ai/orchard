# Design: Agentic Execution Profile

## Context

`normalize-responses-tool-calling` supplies endpoint-local Responses normalization, typed call history, and correlated call events. `qualify-mlx-tool-calling` supplies provider-normalized calls and one exact MLX/client round-trip qualification path. Model capability admission and manual qualification governance distinguish static artifact evidence, runtime behavior, qualification, and support claims. The retry, cancellation, drain, capacity, and cache contracts already own execution safety.

The missing artifact is a reusable profile that tests those seams together without restating their implementations or promoting one successful client/model run into broad support.

## Goals and non-goals

### Goals

- Define a provider-neutral and client-neutral conformance corpus.
- Require exact immutable identity for real workload qualification.
- Keep production activation explicit and later than qualification.
- Make every required behavior measurable from expected events, outcomes, usage, and side effects.
- Use OpenCode as the first conformance client without making it the protocol authority.

### Non-goals

- Implement the corpus or runtime behavior in this contract-only change.
- Add an Orchard-owned agent loop or execute client tools in Orchard.
- Add public API fields, `json_schema`, or `parallel_tool_calls=true`.
- Activate or claim support for Qwen3.8, another model, OpenCode generally, or another client.
- Add or select a runtime provider, including TensorFold.

## Decisions

### Compose existing contracts instead of duplicating them

The profile cites existing endpoint and runtime behavior as prerequisites. It adds only the cross-seam evidence matrix, immutable qualification identity, and activation boundary. Typed call serialization remains owned by the Responses contract; provider parsing remains owned by Worker Runtime conformance; cancellation, retries, capacity, and cache behavior remain owned by their existing contracts.

### Start with a deterministic corpus

The first implementation task is a reusable corpus driven by a scripted provider-neutral inference fixture. Each case declares request input, ordered API and runtime events, terminal outcome, usage, client decisions, and expected tool side effects. This makes client/protocol defects reproducible before model sampling, hardware, parser, or runtime variability is introduced.

The same corpus interface is then reused for named-client integration and exact-tuple real-runtime qualification. A real-model success cannot replace a deterministic failure, and a deterministic pass is not model qualification.

### Keep three evidence boundaries independent

Protocol conformance proves that one exact client integration and Orchard exchange the accepted protocol correctly. Exact-tuple workload qualification adds immutable model, artifact, renderer, parser, runtime, Orchard, client, hardware, environment, and configuration identity plus semantic workloads. Production activation additionally requires approved repository governance, applicable profile gates, and an explicit operator decision.

No boundary automatically advances the next. In particular, the initial OpenCode run is evidence only for its exact version and configuration. It cannot claim general OpenCode compatibility, another client, another model, or another runtime.

### Preserve client ownership and schema boundaries

Orchard returns function calls and accepts correlated results. The client owns tool authorization, semantic validation of generated arguments against the effective caller schema, execution, result continuation, and loop limits. The corpus exercises tool schemas generated by the client adapter and schemas supplied directly by a caller, and proves that invalid generated arguments cause no tool side effect.

Orchard retains its accepted request-shape validation. This profile does not silently add server-side JSON Schema semantics. Structured-output coverage is limited to the currently accepted JSON-object mode; `json_schema` remains an explicit future contract.

### Require proven native drain before capacity release

A disconnect case passes only when evidence shows the provider's native generation operation stopped and drained before Controller allocation or Node/placement capacity became reusable. HTTP, SSE, BEAM, or gRPC closure and a cancel acknowledgement are not sufficient on their own. Unresolved execution remains governed by quarantine and cannot be treated as free capacity.

This is additional Agentic Execution Profile acceptance evidence, not a silent rewrite of the base cancellation authority. `SPEC.md` §4.6.2 may resolve the product's transport-level cancellation and quarantine decision from affirmative runtime-stream closure, but that evidence alone cannot qualify an exact tuple for this profile. Any future change that makes native drain the global capacity-release authority requires a separate reconciliation of the capacity and runtime contracts.

### Treat cache affinity as identity-sensitive but non-authoritative

The corpus compares only opaque Controller-derived identities under one fixed Controller key scope and fingerprint configuration. Equal canonical prefixes covered by that configuration must match. A change to instructions, messages, tool definitions, calls, or results must differ only when the changed canonical bytes are inside the bounded fingerprint domain; changes after the covered prefix may legitimately retain the same identity. The public `prompt_cache_key` hint remains ignored. This profile does not invent a separate full-input identity. A match can affect ranking only through existing bounded fail-open affinity rules and never proves correctness, residency, authorization, or dispatch eligibility.

### Scope terminal and usage assertions

Exactly-one terminal assertions apply at distinct boundaries. Every admitted logical Request has one durable terminal outcome. Each conforming Runtime Endpoint execution stream that begins has one terminal, so two attempts may correctly produce two runtime terminals. A public request has at most one deliverable terminal when its connection remains available; disconnect does not require delivery. Pre-dispatch rejection has no runtime terminal, and each continuation request in a client-owned tool loop is a separate logical Request. A missing runtime terminal is an injected failure case that must not be converted into success.

Usage assertions likewise follow attempt evidence. Worker-originated terminals require exact cumulative totals. Controller-synthesized terminals may carry the latest validated cumulative count with `output_usage_status = lower_bound`; the corpus verifies the value and status rather than demanding fabricated exactness.

### Declare endpoint and mode applicability

| Behavior | Responses | Chat Completions |
| --- | --- | --- |
| typed text and tool calls | Positive sync/stream lifecycle | Positive sync/stream lifecycle when included in the claimed envelope |
| omitted reasoning | Preserve `model_default + legacy_blended`; do not reclassify delimiter-like text | Same |
| explicit `final_only` | Dependency-blocked until the concrete public field contract is accepted, then positive | Same |
| structured reasoning | Negative rejection under the current contract | Negative rejection under the current contract |
| structured JSON object | Negative unsupported-field case; no selector is defined | Positive sync/stream `json_object` cases |

Every executable assertion is pass/fail. A contractually expected rejection is a passing negative case but not a positive capability. A positive case waiting on an unaccepted public contract is `dependency_blocked`, not simulated through internal canonical fields and not counted as conformance.

## Gate matrix

| Gate | Deterministic passing evidence | Exact qualification addition |
| --- | --- | --- |
| Final text | Exact typed items/deltas and final value | Repeated semantic assertions |
| Reasoning | Negotiated separation or expected fail-closed rejection | Exact tuple, parser, projection, and effort when applicable |
| Tool continuation | Stable IDs, ordered result continuation, zero Orchard tool side effects | Real client executes only validated synthetic tools |
| Structured output | Valid exact JSON object and malformed failure | Repeated exact semantic values |
| Schemas | Generated and caller-supplied request shapes; client rejects invalid generated arguments before execution | Exact client schema implementation/version |
| Usage | Exact Worker totals or correctly classified Controller lower bounds; zero/missing distinction; stream/sync agreement | Runtime terminal accounting on the exact tuple |
| Terminal | One logical-Request outcome and one terminal per begun conforming runtime stream; scoped public delivery | Failure and missing-terminal injection on the real runtime |
| Disconnect | Cancel plus profile-level native drain evidence precedes observed capacity reuse | Provider-native stop/join evidence on target hardware |
| Cache | Opaque equality/difference matrix within a fixed bounded fingerprint domain; hint ignored | Affinity observation without correctness or eligibility claims |
| Retry/errors | Closed errors, bounded retry, pinned identity, no duplicate side effect | Real transport/runtime failure injection |

Every executable row is pass/fail. Unsupported requested behavior passes only the negative case when the contract requires rejection; it does not become a positive capability claim. A dependency-blocked positive row remains unpassed.

## Rejected alternatives

### Use the first OpenCode and model run as the profile

Rejected because a client/model demonstration combines protocol, semantic, hardware, and configuration variables and cannot establish a reusable neutral contract.

### Put the agent loop in Orchard

Rejected because base v1 deliberately returns calls for client execution. It would introduce hosted execution authority, policy, persistence, and failure semantics outside this change.

### Treat qualification as activation

Rejected because model qualification governance explicitly separates evidence from support claims and runtime state.

### Adopt a new runtime foundation

Rejected because this profile composes public and provider-neutral contracts. TensorFold or any other runtime foundation would require a separate runtime-provider proposal and acceptance evidence.
