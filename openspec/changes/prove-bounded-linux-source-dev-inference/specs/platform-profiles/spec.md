## MODIFIED Requirements

### Requirement: Unmanaged Linux Source Development Is A Compatibility Workflow

Orchard SHALL distinguish `linux_unmanaged_source_development_compatibility`
from every platform, distribution, runtime-provider, and acceptance profile.
On Ubuntu 24.04 x86_64 it MAY run the portable Orchard applications from a
developer-owned checkout with the pinned developer toolchain, disposable local
development PostgreSQL, repo-local development identity, loopback HTTP, and the
loopback gRPC compatibility path.

The baseline workflow SHALL remain model-free, unsupported, and unqualified. It
MUST NOT create or imply production Node inventory, enrollment or admission,
credentials, Peer Grants, scheduling, placement or capacity authority,
provider or model qualification, inference support, root-owned singleton
custody, fixed appliance roots, systemd or cgroup enforcement, packaging, or
support. Its evidence MUST NOT satisfy or replace KAP-95, KAP-103, the accepted
Ubuntu single-host profile, or any Linux Controller, Linux Node,
mixed-platform, or runtime-provider gate.

A separately owner-authorized proof of concept MAY temporarily exercise one
immutable provider/model/hardware tuple through the existing Orchard API,
scheduler, Runtime Endpoint, and Worker Runtime path. It SHALL use only
loopback or owner-only socket transports and disposable development state,
record every compatibility shortcut, and remove all proof-owned state. For this
proof only, an owner-invoked wrapper MAY supervise the loopback provider outside
Node Agent child custody while the Agent supervises the Worker adapter. Passing
SHALL prove only the exact direct-API and installed OpenCode API-client paths
exercised and
SHALL NOT create any production authority, custody precedent, provider/model or
coding-agent qualification, reliability, capacity-release, or support claim.

For the exact proof tuple only, the development Worker adapter MAY apply one
pinned artifact-bound parser after an owner-only disposable registration selects
the exact `enabled + final_only + medium` render contract and official sampler.
It MAY discard reasoning without retention, normalize complete validated
model-native tool blocks, emit only final answer text and tool events, and fail
closed on malformed, incomplete, unknown, unrequested, or ambiguous output.
The registration MUST bind the imported artifact and chat template and reject
implicit/default or `xhigh` behavior. This exception MUST NOT create production
reasoning advertisement or negotiation authority and MUST NOT be available
outside the disposable exact tuple.

#### Scenario: Model-free developer smoke succeeds

- **WHEN** a contributor runs the all-in-one source command on Ubuntu 24.04 x86_64 with disposable loopback PostgreSQL, repo-local development identity, and the stub Worker backend
- **THEN** the Controller, Console, migrations, and local Runtime Endpoint compatibility observation may be validated
- **AND** no trusted or admitted production Node, schedulable capacity, Worker process, provider, model, or inference authority is created

#### Scenario: Separately authorized inference proof succeeds

- **WHEN** the exact approved tuple returns the bounded direct-API and OpenCode results through Orchard and cleanup restores the recorded baseline
- **THEN** the result proves only viability of that one developer experiment
- **AND** it proves no Milestone 9 provider pilot or qualification evidence, production custody, cancellation, capacity release, reliability, performance, appliance behavior, KAP-103/KAP-105 completion, or support

#### Scenario: Appliance evidence is requested

- **WHEN** either unmanaged compatibility workflow completes successfully
- **THEN** Orchard continues to require every accepted Ubuntu single-host installation, custody, identity, service, database, recovery, qualification, and support gate
- **AND** the compatibility result cannot be represented as KAP-95 or KAP-103 evidence
