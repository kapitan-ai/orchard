## Context and status

This is a contract-only change, with no production or test changes. `SPEC.md` §7.5.0 remains the apex contract. Acceptance of the exact contract is required before code lands; the amendment does not assert implementation conformance or authorize implementation, issue closure, publication, or merge.

The mapping below was checked against `apps/orchard_node_agent/lib/orchard/node/beam_peer_grant_store.ex` and `apps/orchard_node_agent/test/orchard/node/beam_peer_grant_store_test.exs`. Function names, rather than line numbers, identify the reviewed paths. Both install and load take the same validated parent lock before accessing grant custody. No second lock inode, unlocked inspection, or polling is proposed.

## Decisions

### Two public errors, no automatic store retry

Use two sanitized atoms rather than the generic error plus internal causes. `:beam_peer_grant_store_busy` means confirmed exhaustion of the acquisition contention wait. `:beam_peer_grant_lock_unavailable` means failure to establish the helper/readiness protocol before the store operation begins. A retry is eligible, not guaranteed to work: a missing executable may need operator repair. A single bounded acquisition wait is not an automatic retry.

Callers may propagate either failure without retrying. Any later in-process caller retry loop must explicitly bound attempts and total elapsed time, revalidate the exact authorized generation and current lifecycle, and preserve idempotence. No current caller has such a loop. This proposal deliberately does not select one caller retry or a twelve-second budget. Bootstrap must not interpret either result as absence and retrieve another grant. Preflight and startup verification must remain fail-closed; delivery must preserve the selected descriptor and generation. No Runtime Endpoint operation falls back to gRPC because of these errors.

An OTP supervisor restart or service-manager restart is a new invocation outside the in-process caller-retry rule. Every invocation, including after restart, must revalidate the exact authorized grant and create no second durable side effect. `Orchard.NodeAgent.Application.child_specs/0` sets startup bootstrap to `retrieval: :forbid`; `BeamPeerGrantBootstrap.load_or_retrieve/7` therefore only loads and propagates missing rather than retrieving on startup or restart. This rule preserves that load-only startup boundary, not a promise that supervision supplies a retry budget. OTP's default three restarts per five-second window is a rate limit, and launchd KeepAlive with a ten-second throttle has no finite attempt cap; neither satisfies the finite attempt and elapsed-time bound required of an in-process caller retry loop.

### Native acquisition signals and candidate usability

Both supported lock backends must positively identify contention before readiness. macOS `lockf -s` reports acquisition timeout as exit 75 (`EX_TEMPFAIL`); Linux `flock` must receive `--conflict-exit-code 75`. Only exit 75 received before the readiness marker and before the outer readiness guard expires establishes store busy. After readiness, status 75 belongs to the wrapped command, not acquisition. If the outer guard expires first, even a later 75 remains lock unavailable. Generic exit 1 and elapsed time alone never establish contention. These native numbers are subordinate implementation requirements, not platform eligibility or new timeout values.

Extend `validate_lock_candidate/2`'s existing lstat validation to require both owner read and owner write bits on an existing regular, same-owner candidate before spawning the helper. A failure is terminal store invalid with cause `:lock_file_open_failed`. Mode `0000` is unusable, not evidence of leaked grant material. Preserve candidate absence and permitted later initialization narrowing; the precheck does not require an already exact `0600` mode.

Do not classify permanence from helper open-failure statuses or parse stderr. Linux open failures span 66, 71, and 73, and macOS lockf uses 73 for open failures including descriptor exhaustion. A helper open failure after the candidate passes validation is an unexpected pre-readiness exit and remains lock unavailable. Unsupported OS is different: `lock_process/1` has no supported backend and remains terminal store invalid with cause `:unsupported_host`. A missing executable on a supported backend, including Linux without util-linux, remains lock unavailable because operator repair can restore that backend.

### Terminal custody takes precedence

Do not relabel generic filesystem errors or arbitrary rescued exceptions as contention. Known unsafe custody and failures that leave custody or exclusion indeterminate stay terminal. In particular, losing the helper after the operation starts is not equivalent to failing to acquire it: publication may already have occurred without provable uninterrupted exclusion. Lock loss observed by the post-operation continuity check overrides every operation result with terminal store invalid, including operation errors and raw absence. This preserves today's `with_store_lock/4` behavior: `finish_install/5` and `rollback_expired_publish/6` can mutate before returning a lifecycle error, so an operation error does not prove mutation-free execution. `load/3` maps `:enoent` to missing only after `with_store_lock/4` returns; observed loss must never surface as missing. A subsequent independently invoked install may still succeed idempotently. A live port is not proof that the helper has not exited; the check does not guarantee detection of every helper death.

This preserves permitted initialization narrowing: install may narrow the store directory under the existing rules, while both install and load narrow and validate the regular lock file in `finish_lock_acquisition/3`. Load does not repair unsafe grant-store directories or grant files. A stale regular lock file and its contents are not evidence that a process still holds the kernel lock. Do not infer contention from contents or PIDs.

### Sanitized attribution

Returned errors contain only stable atoms. Diagnostics, logs, and telemetry use only the closed cause-atom set enumerated in `specs/peer-grant-store-errors/spec.md`; cause labels do not determine retryability. Never attach arbitrary OS terms, helper bytes, exception terms, certificates, hashes, paths, PIDs, lock-file contents, grant material, or other host detail. Cause attribution does not introduce additional public retryable errors or make a terminal failure retryable.

### Signals that cannot identify the underlying cause today

Every returned path above has a proposed disposition, but today's undifferentiated helper exit status branch cannot prove contention versus helper malfunction, and its six-second guard cannot prove whether the kernel lock was busy. Later implementation must pin exit 75 on both backends and classify it only before readiness and guard expiry. The exact-message branch cannot distinguish valid split/coalesced marker delivery from malformed output. Later implementation must establish deterministic native-helper outcomes and bounded framing; it must not guess `store_busy` from elapsed time or a generic nonzero exit.

The final `Port.info` check likewise cannot determine when exclusion was lost relative to publication, and can still report a live port after the helper exits. Loss observed by that check is terminal store invalid; the contract does not promise detection of every exit. PR #563's regression orders helper exit after publication and waits for the port's `:DOWN` before the post-operation check. Preserve that deterministic ordering without changing the test in this contract-only change.

## Existing tests and later regression coverage

Existing tests cover exact/idempotent installation, first-store serialization, load/publication overlap, genuine absence, unsafe load custody and symlinks, malformed stored data, temporary cleanup failures, cross-VM exclusion, stale lock reuse, owner death, bounded native arguments, missing helper, non-regular lock candidates, creation hook failure, helper exit before teardown, secret/hash mismatch, lifecycle checks and rollback, and certificate-authenticated client behavior.

The contention and missing-helper tests currently assert generic store invalid; later implementation must change those expectations and add the missing load and framing/error-propagation cases rather than fossilize the residual result. Adding the Linux contention-exit arguments requires updating both the bounded-native-arguments assertion and the helper-exit-before-teardown fixture's hard-coded `lockpath="$5"` position. That fixture already demonstrates that a grant can exist when the operation reports failure. Preserve its terminal safety case and PR #563's release-after-publication and port-`:DOWN` synchronization. This contract-only change leaves the test file unchanged.

The Node-store-to-CLI/Console shared diagnostics surface does not exist today. Later implementation must create that surface, preserve the stable acquisition and terminal store errors, and test their attribution and sanitization through both CLI and Console. Adding the terminal store errors to the §7.5.0 vocabulary defines the required diagnostic contract, not an existing runtime capability.

## Dependency reconciliation and alternatives

- [PR #159](https://github.com/kapitan-ai/orchard/pull/159) landed as an intentional partial precursor. Keep its single validated parent lock and exact-grant load behavior; the remaining long-wait diagnostics gap is this contract's concern, not a reason to replay the precursor.
- The [later decision on #146](https://github.com/kapitan-ai/orchard/issues/146#issuecomment-5174264398) supersedes its earlier independent-readiness clarification. This contract defines the public boundary but does not independently authorize framing work, raise timeout values, start implementation, or close #145/#146.
- Rejected alternative: retain only generic store invalid and add sanitized causes. That leaves callers unable to distinguish terminal custody from acquisition availability.
- Rejected alternative: add one caller retry within a twelve-second budget. Caller retry policy is not selected here; no such retry is introduced implicitly.

## Acceptance and remaining qualification

Lock-candidate usability, host-specific contention signals, observed-loss precedence, unsupported-host classification, and restart accounting are defined above; no classification decision remains open. The unconfirmed readiness-deadline and observed post-operation-loss boundaries remain unchanged. Exact-revision acceptance and independent final-head review remain gates, not implementation-conformance evidence. Later implementation still needs measured contention evidence and host-native exit/framing tests under #146, with public-interface, restart-invocation, and caller coverage under #144/#145.
