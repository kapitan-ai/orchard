## Context and authority

`SPEC.md` §12.2 owns worker-crash recovery. Section 5.10 owns separate Controller attempt-derived breakers, and §§3.7.1/5.9 own closed Request retry and evidence. This design resolves the implementation choices for #379; it does not adopt Controller breaker expiry, crash metrics as policy history, or Request replay.

The existing seams are `Orchard.Node.ModelManager` for workers, single-flight loads and monitored exits; `WorkerProcess` for current runtime/generation events; `WorkerSupervisor` for temporary children; and `RuntimeEndpointMapper` for observations. Keep policy out of OS custody and do not switch children to OTP automatic restart.

## Decisions and rationale

### 1. Identity and qualifying events

Policy key: `(stable node_id, model_id, version)`, using the exact runtime model/version associated with an admitted catalog target. Node identity must be authenticated; an address, worker PID, or §5.10 catalog key is not a substitute. A new model version is independent, not an automatic clear of the old version. Do not permit aliases or a mismatched artifact to relabel the same requested identity and evade its gate; retain existing artifact validation. Unresolved mapping refuses admission.

Count unexpected loss of an admitted loading or loaded managed worker, including current runtime process exit and loss of its current channel that renders it unusable. An unexpected normal-status exit also counts; a nonzero exit is not required. Controller-to-Node transport loss alone is not evidence of a worker crash. A load error, failed spawn before a worker is admitted, missing artifact, resource refusal, or timeout is not by itself a crash. A load error accompanied by actual unexpected worker loss counts once.

Register worker incarnation and load ownership before receiving its asynchronous outcomes. ModelManager serializes event acceptance. A stop intent recorded before observed loss makes the later termination intentional; if loss was already accepted, subsequent unload cannot retroactively erase it. An unload that discovers a worker already dead must record that loss unless prior stop intent proves intentional termination. Deduplicate all DOWN, channel-loss, and load-result reports by admitted incarnation, not by model counter or error string. Fence runtime done by active generation and channel events by current connection identity.

Rationale: counting every failed restart as a crash manufactures the five-crash threshold; counting only loaded-worker deaths misses real loading crashes. Existing cumulative, capped-cardinality crash telemetry remains separate and is not rewritten as a rolling ledger.

### 2. Time, stability, and the capped sequence

Use injected Node monotonic milliseconds. For an accepted event at `now`, retain times strictly greater than `now - 600000`, including the new event. Events exactly ten minutes old are excluded. Count the fifth event and open before considering a restart timer. Wall clocks and Controller observation timestamps do not drive local arithmetic.

Maintain the rolling history separately from the capped delay index. Crash ordinal since reset gives delays `[1000, 2000, 4000, 8000, 16000, 30000]`, thereafter 30000. A successful load starts a stability interval but does not immediately reset either counter. Ten continuous loaded minutes resets both, evaluated before a boundary crash. Loading, waiting, planned unload, and agent downtime are not stability. An open breaker never expires or probes.

Rationale: coupling the delay index to the rolling count makes the 16/30-second tail unreachable; resetting on every successful restart defeats exponential backoff. Sparse crashes can exercise the tail without crossing five in one window.

### 3. State machine and residency ownership

ModelManager is the single mutable authority, assisted by a pure time-injected policy module. Illustrative policy states are `armed`, `backoff`, `restarting`, `open`, and `recovery_required`. Placement lifecycle state remains separate: an open or recovery-required placement is failed; pending backoff is failed with pending recovery, restarting is loading but unavailable, and only completed loads are loaded. Do not misreport a failed runtime as cached or healthy residency.

| Event | Transition/effect |
|---|---|
| Qualifying crash below threshold | Mark worker failed; preserve existing Request terminalization; retain recovery residency intent; reserve one residency slot; enter backoff with no-earlier-than due time |
| Fifth crash in window | Enter open, cancel/fence pending work, admit no restart, release slot only after cleanup resolution |
| Current timer due and cleanup resolved | Revalidate load authorization/resource constraints, enter restarting, start exactly one ordinary load pipeline under recovery ownership |
| Restart succeeds | Enter armed/loaded, start stability interval, keep crash history and index |
| Restart fails with actual worker loss | Accept one crash for that incarnation; apply threshold/backoff |
| Restart fails without worker loss | Enter recovery-required, retain history/index, stop automation and release resolved slot; no synthetic crash |
| Ordinary unload/eviction during recovery | Cancel/fence recovery intent, preserve history/open breaker; if not open, require recovery; no automatic restart after unload |
| Successful explicit recovery | Reset history/index, fence prior work, arm absent or start one forced-reload load |

Backoff reserves one `max_loaded_models` residency slot, not Request dispatch capacity. The load in `restarting` consumes that same slot, not an additional one. Open/recovery-required records do not hold a slot once cleanup is resolved. No unresolved runtime occupancy may be reported as free. Reserved slots do not waive memory/resource/security checks or evict another placement specially for recovery. Failure of those checks stops automation without counting a crash. Restart completion must retain its explicit residency owner even with zero Request waiters; callers do not need to survive for worker recovery to finish.

Every admitted worker must carry enough non-Request model/load identity to restore residency through the existing load pipeline. Missing restart prerequisites fail closed as recovery-required, not an immediate open breaker and not a silently loadable absent placement. Never retain prompt data, generation requests, or expired inference deadlines as restart input. Restart loading uses the current ordinary model-load deadline; inference deadlines remain untouched. Ordinary ensure calls during backoff or restarting are refused rather than bypassing or joining the recovery operation.

### 4. Reset and scoped recovery-state survival

Ordinary internal reset cancels timers and in-flight recovery, resolves cleanup, removes residency ownership, increments fences, and preserves known history and open state. Other interrupted recovery keys become recovery-required; a healthy key with no recovery history can checkpoint a clean intentional stop and load normally later. Reset is not a privileged operator clear or a test-only production bypass.

Persist one current recovery checkpoint per `(node_id, model_id, version)` in Orchard's existing Postgres database. ModelManager owns policy decisions and the live monotonic clock; the authenticated Active Controller owns checkpoint access and compare-and-set durability. The Node obtains hydration and checkpoints through an identity-bound control operation, not database credentials or a local journal. Ordinary observation snapshots are not sufficiently synchronous to serve as this authority.

The checkpoint needs only the exact key, owning recovery epoch, monotonic revision, policy state, capped backoff index, bounded crash history (at most five timestamps scoped to that epoch), stable-operation marker, and current worker/load/recovery-operation ownership phase with opaque incarnation/custody identity sufficient for existing cleanup verification (not a bare PID or a local path). Retain a bounded latest recovery command identifier, payload fingerprint, and outcome for duplicate handling; never model artifacts, prompts, Request payloads, or unbounded events. Use a dedicated `worker_recovery_checkpoints` table with a unique exact-placement key and transactional revision check; resolve its catalog model reference to the exact runtime model/version rather than using free-form caller identifiers. Keep this separate from asynchronously refreshed `model_placements` status so observation writes cannot overwrite policy state. The implementing migration is limited to this checkpoint, not a generic state store. Clean absent checkpoints may be retained; deletion must not erase nonclean state or reopen an old command revision. No TTL on open or uncertain checkpoints.

Write ordering is safety-critical:

1. Hydrate the exact key from the Active Controller. Authoritatively absent means clean; a missing field/cache entry or unavailable database does not. Before the first worker starts, durably claim in-progress worker/load ownership for that key and current epoch/revision. A missing acknowledgement admits no worker, including ordinary cold load. This write-ahead marker closes the crash-before-first-checkpoint hole.
2. On a crash, immediately close local admission and terminalize affected Requests under existing rules. Checkpoint history/backoff/open before any replacement is launched or eligibility is published. If that write fails, the prior in-progress marker survives and the local key stays blocked; repeated persistence attempts do not count additional crashes.
3. On load completion, stable reset, intentional stop, or explicit clear, commit the corresponding checkpoint before publishing the new eligibility/reset or replying success. Clear history only once cleanup is resolved. Acknowledgement loss is uncertainty, not permission to rerun a load or destructive clear. If a stability-reset write is pending when a crash arrives, evaluate stability first and persist reset plus crash in one transition; fence a late reset acknowledgement so it cannot erase that crash.
4. When database/control access is unavailable, existing workers follow §12.6 and existing session/occupancy rules. A pre-effect checkpoint failure defers automatic restart with its original due time and one reserved slot, rather than becoming a non-crash load failure or recovery-required by itself. Retry only the idempotent checkpoint/status exchange with bounded pacing (no more than once per second per key), not worker effects. Resume after confirming the same current transition, provided no reset/unload/new epoch superseded it. Ordinary caller admission may return unavailable under its existing deadline. Do not mark the placement durably clean locally or reinterpret checkpoint transport failure as another worker crash.

A fresh ModelManager/Node Agent uses a new opaque epoch. Bind it using existing authenticated Node/current-incarnation controls and a transactional expected-revision claim; do not allow a new epoch to overwrite an old live owner without resolving its runtime occupancy. Reject late old-epoch checkpoint writes, timers, completions and operator commands. Controller restart alone does not change the Node epoch or authorize a reset.

Hydration rules: retain checkpointed `open` and `recovery_required` as such even with empty history. `backoff`, `restarting`, nonempty crash history or a nonzero delay index, pending restart/load/recovery command, or unresolved prior worker ownership becomes recovery-required after epoch loss, retaining diagnostic history/index and requiring explicit recovery. Do not translate old monotonic timestamps into the new epoch or let downtime expire a breaker. Only `armed` checkpoints with empty history, zero delay index, and checkpointed resolved worker/load/recovery-operation ownership are proven clean; committed loaded ownership alone is not a clean stop. These clean checkpoints, and authoritatively absent/new keys, remain normally loadable. Thus an abrupt agent loss may require recovery of placements it interrupted, but not unrelated healthy keys or a new installation. A clean shutdown checkpoints intentional stop for healthy workers; history-bearing keys still require explicit recovery after epoch loss. An abrupt agent loss, or Controller-first shutdown that prevents clean-stop acknowledgement, can therefore require explicit recovery for every placement that was still resident, but not for cleanly stopped or new keys. Unavailable hydration defers admission, not a permanent startup re-arm requirement.

Prior-epoch cleanup has a concrete completion condition: the new Node has no current worker/load for the exact key, and its existing runtime custody boundary supplies affirmative termination/nonexistence proof for the checkpoint's prior incarnation, or proves the host boot that owned it ended. Empty ModelManager state, a zero local occupancy counter, or PID absence/reuse alone is insufficient. Explicit recovery invokes that cleanup check; on success it checkpoints prior ownership as operator-terminated before resetting/claiming new work. On unknown ownership it returns 503 without clearing and requires operator cleanup using existing host/runtime controls, followed by a fresh recovery command. Do not add a new process reaper or silently adopt an orphan. The implementation may expose a small adapter callback over existing custody, but must test both proven and unknown outcomes.

Rationale: volatile-only state plus implicit clean startup creates a bypass; blanket re-arm broadens normal startup; a local journal violates Postgres sole persistence. A bounded write-ahead checkpoint through the Controller is the minimal durable authority that closes the loss window while preserving Node policy ownership. Scoped fail-closed treatment avoids inventing cross-epoch time arithmetic or an unattended resumption protocol. Tests must cover loss before and after each checkpoint/ack boundary, including a fifth crash whose open write fails: the durable in-progress marker still prevents automatic admission after restart, even if the exact fifth event was not committed.

### 5. Authenticated explicit recovery

Add a dedicated transport-independent `RecoverWorkerPlacement` operation, not an overloaded §5.10 breaker clear. The narrow Operator API surface is:

- `GET /ops/v1/worker-recovery/nodes/:node_id/models/:model_id?version=<exact-version>`: current bounded recovery status, epoch and per-key revision (an authoritatively absent key is clean, with an initial revision).
- `POST /ops/v1/worker-recovery/nodes/:node_id/models/:model_id`: exact version, action `clear | unload | reload`, required current `expected_epoch` and `expected_revision`, bounded nonblank reason, and a bounded command identifier. `reload` means forced reload; `unload` is non-forced.

Use existing Operator authentication, write authorization, Active Controller checks, Node identity resolution, and audit infrastructure. Controller resolves the catalog target to exact runtime model/version and validates the body; arbitrary client runtime identities must not bypass that mapping. Forward a dedicated recovery operation over the authenticated Runtime Endpoint control path. A caller-supplied `operator: true` or ordinary `force: true` is not authority. Node must enforce the control caller identity/authority on BEAM and gRPC paths. Raw endpoint access must not become a backdoor. This adds no UI or general model administration API.

Semantics:

- **Clear:** only absent/failed or automatically recovering placement; cancel automatic load/timers and prove cleanup, then reset and arm absent. If a loaded worker or caller-owned load exists, return conflict without clearing. Clear does not load, infer, or clear Controller breakers.
- **Unload:** successful non-forced operator unload resets and arms absent, even if already absent/open. It cancels pending automatic or caller-owned loads with normal waiter cleanup; active executions cause busy/conflict without reset. A later ordinary ensure is the reload half of unload/reload. A reconciliation unload has no such authority.
- **Reload:** one serialized operation resolves forced-unload cancellation/terminalization, resets, and starts one fresh load under recovery ownership. While in progress, ordinary load/execute and another recovery operation cannot interleave. Return success only when loaded. A failed load without a crash becomes recovery-required; actual worker loss uses normal crash policy. Forced cleanup never authorizes request replay.

The Node is the sole originator of checkpoint mutations, including create, epoch claim, operator operation claim, and completion. The Controller's Operator API handler checks identity/authorization and expected fields read-only, then forwards; it never bumps revision before forwarding. ModelManager serializes the command and originates the authoritative checkpoint CAS through the Controller. Use a per-key operation lock plus expected epoch/revision comparison before any destructive effect. Claiming an operation invalidates the prior revision. Timer/load/worker identities remain separately fenced; an old completion cannot terminate the replacement. Serialize ordinary unload/eviction with recovery: if it cancels an in-progress reload, that operation must finish unsuccessfully and remain recovery-required, not later publish success.

Persist operation claim/phase before effects and final state/outcome before success acknowledgement. Matching duplicate command identifiers/payloads within the retained current-epoch operation result return that result without new effects. Reusing an identifier with different payload conflicts. Retain only a bounded latest-operation result per key; an older command whose result is no longer retained fails the expected-revision check, never re-executes. Busy/conflicting commands that perform no effect do not reset state. On timeouts/unreachability return unavailable/unknown outcome, not success; the caller re-reads status and must not automatically substitute a new epoch/revision to repeat destructive work. A fresh epoch rejects old commands; an interrupted operation requires explicit recovery after occupancy resolution rather than automatic continuation. No distributed exactly-once completion is claimed.

Use 200 for a completed successful operation/status, 409 for stale epoch/revision, incompatible live state or operation conflict, 422 for invalid input, and 503 for unavailable endpoint or unresolved cleanup/load failure. Existing authentication and Active Controller error mappings retain precedence. Bounded responses report key, epoch, revision, recovery state, and stable reason; audit accepted/completed/failed recovery with non-content metadata in existing audit facilities. Do not report an audit write failure as successful recovery; uncertain delivery requires status inspection, not blind replay.

### 6. Evidence, no bypass, and compatibility

Report endpoint recovery epoch/hydration validity plus per-key recovery revision, state, and allowlisted reason; for backoff, an advisory remaining delay may be included. Do not export a monotonic timestamp as a Unix timestamp or allow Controller time to release backoff. Retain open/recovery-required evidence after worker removal. Use the existing transport-neutral Observation and Placement seams and existing durable observation payload facilities. These are scheduling projections, distinct from the synchronous bounded checkpoint in decision 4.

Carry exact identity and epoch/revision through Node status → RuntimeEndpointMapper → shared Observation/Placement → Controller observation normalization → scheduler snapshot → final revalidation. Preserve the existing authenticated freshness and observation-order rules; an older observation cannot overwrite a newer one. Epochs are opaque, not lexically sortable. Bind current epoch to the authenticated current endpoint session/observation sequence; after session change or uncertainty require fresh status, not cached loaded evidence. Missing support is unknown/ineligible, never a legacy-loaded fallback around the recovery gate.

Apply the gate before loaded fast paths as well as cold paths, ranking, capacity acquisition, reconciliation load admission, and final execution acceptance. During backoff/restarting or open/recovery-required, Node refuses ordinary ensure and execution even if stale Controller evidence says loaded. Existing Controller §5.10 breaker gates still apply independently after explicit Node recovery. Other model/version keys and other Nodes remain usable; local recovery failure is not a Node-wide health failure.

Supported BEAM and gRPC compatibility adapters must carry equivalent status/refusal/recovery semantics, with additive protocol fields/operations only where required. Legacy or malformed recovery evidence must fail closed for the affected endpoint, not infer armed status. Exact encoding/regeneration is an implementation seam, not permission to expand protocol ownership or add unrelated storage. An authenticated reverse control operation for hydration/checkpointing is required as well as the Controller-to-Node recovery command; its adapter must preserve current Node/Controller identity and transactional revision checks. If existing observation payloads cannot preserve the required projections, keep any schema adjustment restricted to these fields.

### 7. Refusal and real-failure accounting boundary

Admission refusal is a structured recovery result distinct from a `ModelLoadFailure`, with no runtime load started:

| Local condition | Stable endpoint/explanation reason |
|---|---|
| backoff | `worker_restart_backoff` |
| restarting / serialized recovery load | `worker_restart_in_progress` |
| open | `placement_crash_breaker_open` |
| lost state / non-crash recovery failure / stopped recovery | `placement_recovery_required` |

Do not use `RUNTIME_UNAVAILABLE` model-load category as a catch-all transport encoding: it invents a load attempt, makes the refusal retry-capable, and manufactures §5.10 evidence. Handle the structured outcome before generic load-failure conversion.

Before `request_step.started`, candidate rejection uses existing no-eligible-candidate and bounded queue behavior, with no attempt or breaker event. After an attempt starts, a proven no-execution refusal maps to existing `capacity_rejection` + stable `model_busy`, model-load category nil, and ordinary capacity release. Here capacity means this placement has no admissible execution capacity under recovery policy, not a new crash or transport failure. No retry vocabulary/eligibility changes are needed: existing gates apply unchanged. Existing identity/occupancy uncertainty and cancellation/deadline precedence must not be overridden by this normalization. Public response uses the existing model-busy mapping; local reason codes do not extend durable Request error vocabulary or metric labels.

By contrast, an actual Request attempt's worker death or model load failure retains its existing closed class and §5.10 attribution, even if it also causes Node recovery. Count it only once per existing attempt accounting. A scheduled residency restart has no Request attempt and therefore cannot manufacture Controller attempt evidence. Clearing either policy does not clear the other. Tests must prove these boundaries rather than declaring dispatcher/classifier integration unnecessary.

### 8. Minimal implementation interfaces

These are semantic interfaces, not a new general coordination service:

| Interface | Caller → authority | Minimum input and result |
|---|---|---|
| `WorkerCrashPolicy.transition(record, event, now_ms)` | ModelManager → pure policy | Returns next policy record plus declarative effects (`checkpoint`, `schedule`, `load`, `refuse`); reads no clock, database, or process state |
| `ReadWorkerRecoveryCheckpoint(key)` | Node → authenticated Active Controller | Returns `absent`, full bounded checkpoint/revision, or `unavailable`; only a successful authoritative read can establish absence |
| `CommitWorkerRecoveryCheckpoint(key, expected_epoch, expected_revision, transition_id, next_record)` | Node → authenticated Active Controller/Postgres | Atomic insert-if-absent or CAS; returns committed revision/record, matching already-committed result, stale conflict, or unavailable; transition ID/fingerprint distinguishes lost-ack replay from a second mutation |
| `InspectWorkerRecoveryPlacement(key)` | Active Controller → Node | Hydrates the exact key if needed and returns current-epoch recovery eligibility/revision without loading or clearing; permits clean new cold keys to obtain positive evidence before ranking |
| `RecoverWorkerPlacement(key, expected_epoch, expected_revision, command_id, action, reason)` | authorized Active Controller → Node | Node serializes, verifies prior cleanup if needed, originates CAS/effects, returns bounded completed state/result or conflict/unavailable; API handler never pre-claims |
| `resolve_prior_worker_ownership(key, custody_identity)` | ModelManager → existing runtime custody adapter | Returns `resolved` only with affirmative old-incarnation/host-boot proof, otherwise `unresolved`; never equates an empty new process map with proof |
| recovery observation projection | Node status → Controller snapshot/evidence | Current authenticated epoch, per-key revision/state, hydration validity, bounded reason; independent of live loaded-model list, never a checkpoint write |

Operator `expected_epoch` addresses the current Node recovery epoch. Hydrated status also retains the checkpoint's prior owner epoch separately when different. The Node uses that persisted owner epoch plus revision as the CAS expectation, and may write its current epoch only after the required prior-ownership resolution; it never treats a row-epoch mismatch as absence. A key's revision remains monotonic across epoch claims. `InspectWorkerRecoveryPlacement` is also the narrow status source for the Operator GET and for cold candidates lacking exact-key evidence; it does not require prior load or operator re-arm. Do not infer positive readiness from an omitted placement entry.

`transition_id` is an epoch-scoped monotonic per-key sequence or unique bounded ID. The checkpoint retains the latest applied transition ID and fingerprint, so an identical retransmission returns its committed result, while a superseded transition conflicts. Exact worker/load/recovery identities fence effects separately from checkpoint revision: a new crash while persistence is pending must not be lost or double-counted. Writes are serialized per key; late acknowledgement cannot publish older eligibility.

Do not synchronously hold a Controller checkpoint transaction or ModelManager receive loop across a cross-direction RPC: forward/await work outside the Controller transaction; ModelManager tracks pending checkpoint/load continuations and handles current worker loss/cancel/unload meanwhile. This avoids Controller→Node recovery calls deadlocking on Node→Controller checkpoint requests. Hydration/epoch claims retain prior nonclean state and cannot clear it; a new owner is established only under existing authenticated incarnation fencing and prior-occupancy resolution.

## Deterministic acceptance matrix

- Delays: crashes at 0/150/300/450/601/752/903 seconds yield 1/2/4/8/16/30/30 seconds with at most four crashes in each half-open window; successful intervening loads remain below ten continuous loaded minutes. Independently test production constants and no-earlier-than timer admission.
- Trip: five closely spaced actual crashes after eligible restarts open on the fifth; no fifth restart timer, probe, ordinary load, or alternate fast path can execute.
- Boundary: an event exactly 600 seconds old is excluded, one millisecond newer included; stability resets exactly at ten loaded minutes, but not while loading/backing off.
- Definition: loading-worker death versus ordinary load error, current channel versus Controller disconnect, normal unexpected exit versus intentional stop, unload finding a dead worker, duplicate DOWN/load result, stale done/channel/timer/completion.
- Ownership/capacity: waiter-free restart persists residency, no request replay, single slot through backoff/restart, other placement admission after resolved open, unresolved cleanup never frees capacity, non-crash resource/load failure stops automation without counting.
- Recovery: clear, absent non-forced unload, busy non-forced unload, forced reload success/failure, ordinary force/reconciliation unable to clear, overlapping command/timer/unload, timed-out command status inspection, duplicate command after a new crash, epoch/revision mismatch.
- State loss: reset preserves open/history and cancels/fences timers; clean/new keys load normally; interrupted/history-bearing keys require scoped recovery. Test database loss and process loss at every checkpoint/ack boundary, hydration unavailable versus authoritatively absent, failed fifth-crash persistence, stale checkpoint writes and old-epoch commands. Controller-only restart does not clear Node state.
- Evidence/accounting: loaded/cold/final-admission paths, identity/version isolation, missing/stale/conflicting/old-epoch evidence, BEAM/gRPC parity, structured refusal with zero §5.10 events, real failed attempt's unchanged attribution, closed retry declines and Request terminalization unchanged.

## Bounded implementation handoff

1. **Node authority and checkpoint:** pure policy and deterministic tests; bounded Postgres checkpoint/revision transactions and authenticated hydration/write path; ModelManager state/ownership/timers/reset/recovery; worker event fences and cleanup regressions. Keep temporary supervision and crash metrics intact.
2. **End-to-end enforcement:** status/transport evidence and dedicated authorized recovery operation, narrow Operator API routing/audit, Controller normalization and scheduler/final admission; structured refusal mapping plus real-attempt accounting regressions. Do not ship Node policy as complete without these bypass closures.
3. **Verification/handoff:** smallest tests first, affected suites then applicable ordered AGENTS.md workflows/coverage, strict OpenSpec validation, and sanitized recovery evidence in the issue/PR. No UI, host suspension, or full pilot qualification. Archive/sync only after implementation acceptance.
